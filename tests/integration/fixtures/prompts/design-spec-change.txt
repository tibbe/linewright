## Steps

### 1. Research prior art and choose an option

Read the spec change, `GLOSSARY.md` if present, the spec and the code the spec change touches. Then call the Skill tool with `linewright:software-design`, and find how the problem has been solved before and choose an option from it, as it says. Start its research sub-agents together, in the foreground, and choose from the reports they return.

### 2. Design the code

A design names the modules the change touches. For each, it says what the module is responsible for and its interface to the other modules. A module is anything with an interface and an implementation: a method or function, a class, a package, a service or a library the code uses. Its interface is everything the other modules must know of it. Everything else the module hides, and the implementer decides it.

Some decisions affect more than one module, and must be made before work on the modules can begin. Those are the design's. The first is the seam, where the option attaches to the code. Choose each as the software-design skill chooses between options: list the ways it could go, write the case against each, and take the one that wins.

Keep the code's structure where it holds up. Change it where the change would add a special case to it, or where the structure makes the problem likely, so that the same kind of problem would come back.

A changed structure covers the modules the change touches, judged against the whole spec rather than the spec change alone.

### 3. Cut the work

A spec change's work is always tickets, one when it fits a session: call the Skill tool with `linewright:to-tickets` and cut the work into tickets to your design.

Cut the work into more than one ticket when it does not fit one session, or when it changes the code's structure: then the structure change is the first ticket, and the behavior change comes after it, blocked by it.

Linewright files the tickets under a tracking issue for the spec change, each labeled `ready-for-agent` and `linewright:designed`, and posts your design there: the implementer of each ticket reads it.

### 4. Output

End your session with a final message that is a single JSON object and nothing else, one of:

- `designed`, with the design and, where the work is cut, the tickets: `{ "outcome": "designed", "design": "<the design, in Markdown, in the template below>", "tickets": [TICKET], "comment": "<Markdown: why the work is cut into these tickets>", "spec_gaps": [SPEC_GAP] }`. Leave `tickets` and `comment` out when the work is not cut.
- `nothing-to-build`, when the code already does what the spec change asks: `{ "outcome": "nothing-to-build", "reason": "<Markdown: why>" }`
- `blocked`, on a spec gap only the maintainer can answer: `{ "outcome": "blocked", "question": "<the question the maintainer must answer>", "spec_gaps": [SPEC_GAP] }`
- `gave-up`, when the design cannot be made: `{ "outcome": "gave-up", "reason": "<why>" }`

where

- `TICKET` is `{ "id": "<a short id of your choosing, unique among the tickets>", "title": "<the ticket's title>", "body": "<the ticket's Markdown body>", "blocked_by": ["<ids of the tickets that must be merged first>"] }`
- `SPEC_GAP` is `{ "title": "<issue title>", "body": "<the spec change needed, in Markdown>" }`, and `spec_gaps` lists the gaps that did not block the design (often none).

The design, in this template:


## Spec gaps

The spec is the maintainer's: change no file of it. A question the spec leaves open is a spec gap only when it is a product decision: a reasonable maintainer could want either answer, the answer changes what a user sees, and the spec's wording doesn't already settle it. Anything else is yours to decide, as the spec and the code support best.

A gap that blocks the design is the question of a `blocked` result. For a gap that doesn't, choose the reading the spec and the code support best, carry on, and list it in `spec_gaps`.
